<objective>
Turn the stream into surveillance: watch FDA labels, compare signals against labels, and raise alerts when something changes.

Purpose: A strong FAERS signal for a side effect the label does not mention is the case a pharmacovigilance reviewer most wants to see. Kafka joins the label stream with the signal stream to find it.
Output: Label watcher, label-text check with measured accuracy, alert detector, Surveillance area in the app.
</objective>

  <name>Task 1: Label watcher</name>
  <files>backend/ingest/label_watcher.py, backend/ingest/producer.py, backend/db/schema.sql, backend/db/migrate.py, backend/tests/test_label_watcher.py</files>
  <read_first>backend/clients/openfda.py</read_first>
  <action>
1. Once a day the producer fetches the openFDA label for each watched drug. A drug is watched if it is on the watchlist or has a signal in the latest quarter, capped and rate-limited to stay inside the API key's quota.
2. `label_snapshots(rxcui, set_id, version, effective_time, sections_json, fetched_at)` stores the boxed warning, warnings and precautions, and adverse reactions sections.
3. When the version or effective time changes, diff the sections and publish `label-change` with the drug, the sections changed and the added sentences.
4. The first fetch for a drug only stores the baseline and publishes nothing, so day one does not flood the feed.
5. Tests use saved label JSON: an unchanged label publishes nothing, an added boxed-warning sentence publishes one event, and a reworded label lists the added sentences.
  </action>

  <acceptance_criteria>
    - Running the watcher twice on the same day publishes nothing the second time.
  </acceptance_criteria>
  <done>Label changes arrive as Kafka events.</done>

<task type="auto">
  <name>Task 2: Is this side effect in the label text?</name>
  <files>backend/services/label_check.py, backend/validation/label_check_benchmark.py, backend/validation/reference/label_check_gold.csv, backend/tests/test_label_check.py</files>
  <action>
1. `label_check.find(rxcui, pt)` searches the stored label sections for the Preferred Term, its lower-level wording from `pt_dictionary`, simple variants (plural, "-ia" versus "-ic"), and a small reviewed synonym file. It returns `in_label_text` with the section and sentence, `not_found_in_label_text`, or `no_label`.
2. The wording is always "not found in label text", never "unlabelled" or "unknown". The match is text-based, and a label can describe an effect in words the matcher does not know.
3. Measure it: a gold sample of 150 signal pairs, labelled by reading the label. The CSV records who labelled each pair and is marked "author-labelled, pending faculty review". Report precision and recall of `not_found_in_label_text` on the Methods page.
4. Tests cover exact, variant, synonym, section reporting and the no-label case.
  </action>
  <verify>venv\Scripts\python.exe -m validation.label_check_benchmark</verify>
  <acceptance_criteria>
    - The measured precision and recall are published whatever they are.
  </acceptance_criteria>
  <done>Each signal shows whether its effect is in the label, with a known error rate.</done>
</task>

<task type="auto">
  <name>Task 3: Alert detector</name>
  <files>backend/ingest/consumer.py, backend/services/surveillance.py, backend/db/schema.sql, backend/tests/test_surveillance.py</files>
  <action>
1. Table `surveillance_alerts(kind, rxcui, pt, quarter, detail_json, status, created_at, reviewed_by, reviewed_at, UNIQUE(kind, rxcui, pt, quarter))`. Kinds: `new_signal`, `not_in_label`, `label_change`. Statuses: `new`, `reviewed`, `dismissed`, `escalated`.
2. On `signals-updated` (from 10-03), compare quarter Q with Q-1 from the Spark output. A pair that becomes a signal in Q gives `new_signal`; if `label_check` also says `not_found_in_label_text`, it gives `not_in_label` instead.
3. On `label-change`, raise `label_change` and link it to any existing alert for the same drug whose PT appears in the added text. That link is the moment the label caught up with a signal.
4. All writes are upserts, so replaying events changes nothing (same test pattern as 10-01).
5. Rank the feed by kind, then IC025, then case count. Cap the feed per quarter and show the total, so a quarter with hundreds of new pairs stays readable.
  </action>
  <verify>venv\Scripts\python.exe -m pytest backend/tests/test_surveillance.py -q</verify>
  <acceptance_criteria>
    - A fixture where one pair crosses the threshold gives exactly one alert; replaying it gives none.
    - The consumer reads Spark's results; it computes no statistics.
  </acceptance_criteria>
  <done>New signals and label changes become reviewable alerts.</done>
</task>
