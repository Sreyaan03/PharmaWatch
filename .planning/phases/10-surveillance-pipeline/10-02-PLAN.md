<objective>
Make the system scale-ready: the same code runs on one laptop today and on a cluster later, with only configuration changed.

Purpose: Scaling out later should not mean a rewrite. The places that tie the app to one machine (files on local disk, jobs in web-server threads, hard-coded addresses, state kept in process memory) are put behind small interfaces now. Each interface has a simple single-machine default and a scale-out backend that is tested.
Output: Storage and queue interfaces, separate worker process, health endpoints, a scaled Compose profile with an automated check, a scaling runbook, and measured scaling on one machine.
</objective>

<principles>
These apply to every Phase 10 plan from here on, and to Phase 11:
1. No address, path, port or credential in code. All of it is read through `core/config.py` from the environment, with single-machine defaults.
2. No file access outside `core/storage.py`, except DuckDB's read path (a configured location).
3. No background thread started by a route. Work goes through `core/queue.py`.
4. No per-process state that another copy would need. Caches live in MySQL or Redis-compatible storage, jobs in the jobs table, and files in storage.
5. Every component can be stopped without taking down the core app (signals, interactions, prescription review).
6. Each scale-out backend is exercised by a test or by the scaled Compose check, so it does not rot.
</principles>

<task type="auto">
  <name>Task 3: Queue interface and workers</name>
  <files>backend/core/queue.py, backend/core/jobs.py, backend/workers/run.py, backend/services/prescription/service.py, backend/services/signals.py, backend/tests/test_queue.py</files>
  <read_first>backend/core/jobs.py</read_first>
  <action>
1. `core/queue.py`: `submit(kind, job_id, payload)` and a handler registry. Two modes:
   - `inline` (the default): today's in-process thread pool.
   - `kafka`: publish to topic `jobs.<kind>`. Topics are created with several partitions so worker count can grow later without changes.
2. `workers/run.py --kinds prescription,ner`: a separate process that joins the consumer group for those kinds and runs the same handlers. Workers record progress through the jobs table, so the web app reports status the same way in both modes.
3. A worker crash leaves the job claimable. The job row carries a lease with an expiry, so another worker picks the job up and no job runs twice to completion.
4. Move prescription extraction and review, and NER mining, onto the queue. Routes no longer start threads.
5. Tests: both modes give the same job results on the same input; a killed worker's job is finished by another.
  </action>
  <verify>venv\Scripts\python.exe -m pytest backend/tests/test_queue.py backend/tests/test_jobs.py -q</verify>
  <acceptance_criteria>
    - With `QUEUE_MODE=inline` the app behaves exactly as today with no Kafka running.
    - With `QUEUE_MODE=kafka`, adding a worker container increases throughput with no code change.
  </acceptance_criteria>
  <done>Heavy work can move off the web servers onto any number of workers.</done>
</task>

<task type="auto">
  <name>Task 5: Scaled profile, check and runbook</name>
  <files>docker/docker-compose.scale.yml, scripts/scale_check.py, docs/SCALING.md, reports/validation/scaling.json, backend/validation/report.py</files>
  <action>
1. `docker-compose.scale.yml` (overlay): 2 web copies behind Caddy, 2 workers, MinIO, Kafka with partitioned job topics, a Spark master with 2 workers, and HBase. Every count is a single number to change.
2. `scripts/scale_check.py` brings the profile up and runs these checks:
   - a prescription through the load balancer;
   - a job finished by a worker on a different container;
   - the Spark job on the cluster with output equal to local mode;
   - one worker killed mid-job with the job still completing;
   - HBase stopped with history served from the fallback.
   It writes pass and fail per check.
3. Measured scaling on one machine:
   - Spark with 1, 2 and 4 workers;
   - 200 synthetic prescriptions through 1, 2 and 4 workers;
   - a load test against 1 and 3 web copies.
   Write the results to `reports/validation/scaling.json` and show them on the Methods page as "measured on one machine; shows the mechanism, not cluster speedups".
4. `docs/SCALING.md` is a runbook with, for each component, what to change to move it to its own machine or a managed service, the settings involved, and known limits: DuckDB stays a per-copy read-only engine; MySQL needs a managed instance or a replica for heavy use; HBase needs region splits planned. It also covers the Kubernetes path: the same images, one Deployment per role, configuration from ConfigMaps and Secrets.
