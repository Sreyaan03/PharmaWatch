<objective>
Give Spark and HBase real jobs: Spark runs the quarterly all-pairs signal computation, and HBase serves the signal history.

Purpose: Today signals are computed only when someone asks about a drug. Surveillance (10-03) and replay (10-04) need every pair, every quarter, computed ahead of time. That is a batch job over about 20M drug rows and 22M reaction rows, which is Spark's job, and its output is a keyed, versioned lookup, which is HBase's job.
Output: Data lake export, Spark job, HBase history table, history API and chart, published timings.
</objective>

  <read_first>backend/faers/disproportionality.py</read_first>
  <action>
1. Spark service (apache/spark 3.5, local mode, Java inside the container) under a `bigdata` Compose profile, with the lake mounted.
2. `spark_signals.py`: for each quarter Q, cumulative from the first loaded quarter through Q, count a (drug with PT), drug total, PT total and N by distinct case; compute PRR, ROR with its lower bound, IC and IC025, chi-square and class with the same formulas as `compute_metrics`. Keep pairs with a >= 3 in any quarter.
3. Write `lake/results/signals_by_quarter/` (Parquet, partitioned by quarter) with the data version, and publish a `signals-updated` Kafka event naming the quarter and the run.
4. Agreement test: for 1,000 sampled pairs and 3 quarters, Spark's values equal `compute_metrics` within 1e-9 and the classes match exactly. A small fixture lake lets this test run in CI with PySpark local mode, skipped when Java is absent.
  </action>

  </acceptance_criteria>
